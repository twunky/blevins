## Implementation summary

- **Concurrency pattern (reused from Concern):**
  1. Look up the Family Group outside the transaction.
  2. Begin a `Serializable` transaction and lock the `FamilyGroups` row with a no-op `ExecuteUpdate`.
  3. Load the Incident and normalize: revoke non-matching grants at `EndedAt`, and freeze at the earlier cause.
  4. Check expiry, then the caller's current grant.
  5. Mutate, write the audit in the same transaction, and commit.

  Row versions on `SafetyIncident` and `IncidentTask` are a second guard. There are no distributed locks.
- **Stale-tracking guard (added during verification):** a concurrency test showed that a long-lived `DbContext` returns already-tracked entities without refreshing them. A stale `CoordinatorGrantId` was then authorized. Production uses a per-request scope, but correctness must not depend on that. The repository now detaches any tracked rows of the Incident aggregate right after taking the Family Group lock (`ForgetTrackedAggregate`), so every decision reads committed state. The test now passes.
- **Grants:** `IncidentParticipantGrant` is the only source of access, including for the coordinator. It is valid only while its captured membership is active at the captured version, with matching account, profile, and group. There is a unique filtered index on (`IncidentId`, `ProfileId`) where `RemovedAt IS NULL`. Re-selection always inserts a new grant.
- **Denied audit:** this follows `DEC-069` exactly. `UPDATE … WITH (UPDLOCK, SERIALIZABLE, INDEX(IX_IncidentAuditEvents_ActorAccountId_Action_UtcHourBucket))`, then an insert if no row was updated. The unique filtered index is on (`ActorAccountId`, `Action`, `UtcHourBucket`) where `DeniedAttemptCount > 0`. No Incident ID is stored.
- **Reconciliation:** `IncidentMaintenanceService` runs at startup and every 2 minutes, and is not registered in the `Testing` environment, as with Concern. Candidates are selected set-based: Open past the inactivity cutoff, Frozen or Resolved past the expiry cutoff, or holding a current grant whose membership no longer matches. Expired aggregates are deleted with set-based `ExecuteDelete` in dependency order, without loading rows. Audit older than 365 days is deleted with one `ExecuteDelete`.

## Implementation choices (non-policy, per the story)

| Choice | Decision |
|---|---|
| Coordinator reference | `SafetyIncident.CoordinatorGrantId`, a plain column with **no FK**. Integrity is enforced by the domain and repository and covered by tests. |
| Concern access query | `IConcernAccessQuery` (`Application/Concerns`) with `CanReadAsync(accountId, concernId)` and creator-only `IsCurrentCreatorAsync(accountId, concernId, familyGroupId)`. It is implemented by `EfConcernAccessQuery` (`Infrastructure/Persistence`) and is read-only (`AsNoTracking`). It mirrors the Concern creator and participant checks plus the effective freeze and 180-day expiry, with no writes. |
| Routes | Exactly the 10 routes in the story's API table. Status codes: `201` for create, add entry, and create task; `200` otherwise; `404` unavailable; `401` no account; `400` validation problem. |
| DTO names | `CreateIncidentRequest`, `ReplaceIncidentParticipantsRequest`, `TransferIncidentCoordinatorRequest`, `AddIncidentEntryRequest`, `CreateIncidentTaskRequest`, `CompleteIncidentTaskRequest`, `CancelIncidentTaskRequest`, `ResolveIncidentRequest`; `IncidentSummaryView`, `IncidentView` (with participant, entry, task, resolution, and timeline item views). |
| Input limits | Reason 1000; entry text and notes 2000; source 500; explanation 1000; task description 500; target label and attempted-by 200; cancel reason 1000; resolution summary, outcome, and optional fields 2000; at most 250 participants. |
| Missing enums | `Kind` and every category are nullable in requests, so a missing value is a validation error. The server applies no default category. |
| Categories by use | Creation reason, task result, and resolution outcome accept `Confirmed`, `Reported`, `Assumption`, or `Unknown` (not `Outdated`). Entry rules mirror Concern: Unknown entries must use `Unknown`; Observations cannot; `Outdated` needs a known original category. |
| Coordinator in a participant list | Listing the coordinator's own profile in a create or replace set is target-dependent, so it returns the uniform unavailable result. |
| Participant self-cancel | Requires a task the caller created, assigned to themself, **under their current grant**. A re-added participant cannot cancel an old-grant task; the coordinator can. This is the narrower reading of the approved rule. |
| Event time | Every entry stores `EventAt` (optional) and `EventTimeUnknown`, and they cannot both be set. A contact attempt requires exactly one. |
| Grant attribution | `AddedByProfileId` and `RemovedByProfileId` on grants support timeline attribution. The creator's initial coordinator grant has no `AddedBy` and is represented by the `IncidentCreated` item. |
| Timeline precedence | `IncidentCreated`, `ParticipantAdded`, `CoordinatorHandedOff`, `Entry`, `TaskCreated`, `TaskCompleted`, `TaskCancelled`, `ParticipantRemoved`, `ParticipantAccessEnded`, `Frozen`, `Resolved` (enum declaration order). |
| Audit shapes | `IncidentCreated` records the subject as the affected profile and the initial `Summary` entry ID. `ParticipantAdded` is written for each initially selected participant. System events have no actor: `Frozen` (`Authorized = true`) and `AccessRevoked` (`Authorized = false`, mirroring Concern). `CoordinatorTransferred` uses `AffectedProfileId` (to) and `FromProfileId`. |
| View helpers | `IncidentView.InactivityFreezeAt` is set only while Open. `IncidentTaskView.NotCompleted` is true for an Open task in a non-Open Incident; the stored status is unchanged. |
| Index names | EF defaults, for example `IX_IncidentParticipantGrants_IncidentId_ProfileId` (unique, filtered), `IX_IncidentParticipantGrants_AccountId_RemovedAt`, `IX_Incidents_State_LastAuthorizedMutationAt`, `IX_Incidents_State_FrozenAt_ResolvedAt`, `IX_Incidents_FamilyGroupId_CreatedAt`, `IX_IncidentEntries_IncidentId_RecordedAt`, `IX_IncidentTasks_IncidentId_CreatedAt`, `IX_IncidentAuditEvents_OccurredAt`, and `IX_IncidentAuditEvents_ActorAccountId_Action_UtcHourBucket` (unique, filtered). |
| Reconciliation batch | 100 candidates per batch, at most 20 batches (2,000 Incidents) per run, every 2 minutes. |

The repository's removal path is covered separately.

- **Freeze before last mutation:** if a membership end is committed with an `EndedAt` earlier than a write that committed in between, the freeze time precedes `LastAuthorizedMutationAt`. This is the canonical "freeze at recorded loss time" rule.
- **Migration timestamp:** `20261002013148` is the UTC generation time, one calendar day after the project date. This is cosmetic.
- **Pre-existing Concern patterns, unchanged and out of scope:**
