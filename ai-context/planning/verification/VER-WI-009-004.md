## Implementation design

### Endpoints

| Endpoint | Success | Every other case |
|---|---|---|
| `GET /api/events/{eventId:guid}` | `200` + `FamilyEventView` | `404`, empty body |
| `GET /api/plans/{planId:guid}` | `200` + `FamilyPlanView` | `404`, empty body |

- Each is mapped in the existing `FamilyEventEndpoints` / `FamilyPlanEndpoints` class, next to the Family-scoped group, with the same `try`/`catch` mapping as the list. `CurrentAccountUnavailableException` → `401`; `FamilyEventUnavailableException` / `FamilyPlanUnavailableException` → `Results.NotFound()`.
- The route has the item ID only. No `FamilyGroupId` is accepted or required (D1).
- A non-GUID ID fails the `:guid` route constraint and gets the framework's `404` with an empty body, as for Trips, Concerns, and Incidents.
- No new endpoint class, DI registration, or `Program.cs` change was needed: the existing `Map…Endpoints` calls wire the new routes.

### Services

`FamilyEventService.GetAsync(eventId)` and `FamilyPlanService.GetAsync(planId)` follow the list's guards:

1. `Guid.Empty` → the domain's unavailable exception, before any account check or repository call;
2. no current account → `CurrentAccountUnavailableException` (→ `401`), before any item lookup;
3. the repository receives the current account ID and the item ID unchanged;
4. a `null` repository result → the unavailable exception.

### Repositories: one visibility query each (D5)

Each repository now has one private query that is the only definition of its read visibility. Both the list and the item read use it.

- **`EfFamilyEventRepository.QueryVisibleEvents(accountId)`:** the caller's **active** memberships, joined to Events in each membership's Family and to the creator profile. It keeps an Event when the membership's profile is its **creator** or has a row in **`FamilyEventAudienceMembers`**. `CanEdit` = creator, or an audience row with `CanEdit` (the unchanged `REQ-PRIV-021` rule). Administrator assignments are not referenced, so they grant nothing.
- **`EfFamilyPlanRepository.QueryVisiblePlans(accountId)`:** the same shape. It keeps a Plan when the membership's profile is its **creator**, **or** `AudienceType == FamilyGroup`, **or** the profile has a row in **`FamilyPlanAudienceMembers`** (the unchanged `REQ-PLAN-005` rule). The creator branch is reached only through an active membership, so a creator who leaves loses access.
- **List (`GetVisibleAsync`):** it keeps its existing active-membership pre-check, so a non-member still gets `null` (→ `404`) and a member who can see nothing still gets `[]`. It then filters the shared query to the requested Family and keeps the same ordering keys: Events `Date, Time, Name`; Plans `Date, Time, ActivityOrDestination`. The pre-check decides only whether the list exists. It is not a second visibility rule.
- **Item (`GetAsync`):** the shared query filtered to the item ID, then `SingleOrDefaultAsync`. It is **one** database query for every outcome. It never looks up the item first, so a missing item and an unauthorized item run the same SQL and both return `null`.
- At most one row per item is possible, because `FamilyGroupMemberships` has a unique index on `(AccountId, FamilyGroupId)`.
- The query projects into a small private query-side class (`VisibleEventRow`, `VisiblePlanRow`) and maps to the view after materializing. EF Core cannot filter or order through a positional record constructor. This is the "anonymous type, then map" pattern the design allows, given a name so the query can be returned from a method. The Plan mapping still uses the existing `ToView`.
- `GetCreatedEventAsync`, which hard-codes `CanEdit: true`, is untouched and is **not** used by the item read (D7).
- The rules stay separate per domain. There is no shared policy class, framework, expression library, or package.

The Design § 4 fallback was **not** needed. The existing list tests passed unmodified on the shared query (see below).

### Unavailable-response equivalence (D2)

- **Repository:** every unavailable case returns the same `null`, from the same single query (SQL tests above).
- **Service:** `null` and `Guid.Empty` both throw the one unavailable exception. No other exception or message exists for these cases.
- **Endpoint:** that exception has one mapping, `Results.NotFound()`, with no body.
- **API tests:** two unavailable IDs, standing for "missing" and "unauthorized", return `404` with a zero-byte body, no `Content-Type`, and identical content headers. A non-GUID ID also returns `404` with an empty body.
- **No `403`** exists on either route. No problem-details body, Family identifier, or wording reaches the caller before authorization.

The API tests use a stub service, as the existing Event and Plan API tests do. The end-to-end equivalence therefore rests on the chain above: SQL-proven `null`, then one exception, then one `404` mapping. No live-database HTTP test was added (see [Known non-blocking issues](#known-non-blocking-issues)).

### Family context (D8)

- The responses are the existing `FamilyEventView` and `FamilyPlanView`, unchanged in the diff. `FamilyGroupId` is the only Family context.
- The API tests assert the exact JSON property set:
  - **Event:** `canEdit, date, description, eventId, familyGroupId, location, name, organizerDisplayName, organizerProfileId, time`
  - **Plan:** `activityOrDestination, audienceType, creatorDisplayName, creatorProfileId, date, expectedCheckInDate, expectedCheckInTime, expectedReturnDate, expectedReturnTime, familyGroupId, notes, planId, time`
- There is no Family name and no audience, editor, recipient, or member list.
- `familyGroupId` appears only in a `200` response. Every unavailable response has an empty body.
