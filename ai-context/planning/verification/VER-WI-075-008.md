## Scenario and browser evidence

Final successful scenario database: **`FamilySafety_Invitation_E2E_57c99a1166bc40c9a2c53702b0dcff88`**.

The Playwright config generates a fresh alphanumeric scenario name per run and passes it to `scripts/start-invitation-scenario.ps1`. That script sets the API connection string to the dedicated name; the existing API invitation-scenario guard rejects a configured database without the `FamilySafety_Invitation_` prefix. The final run created and used the dedicated database; the ordinary `FamilySafety` database was not targeted or reset. Scenario databases are retained as required.

API `/health` returned the plain-text response `Healthy`. Angular became ready at `http://localhost:4200`; Playwright confirmed its Development identity control was visible and Adult A was selected.

The browser journey confirmed:

- A was the default active identity, had the Development Family, and administered it.
- A's Events and Plans endpoints and Trips endpoint returned empty lists at scenario start.
- A created an invitation for `development-recipient@example.invalid`; the Development outbox exposed its invitation link.
- Switching to B selected B, displayed the no-active-Family state, and removed the A Family context.
- Browser requests after switching carried B's Development account header; B's memberships and administered Families were empty, and Family members returned `404` before acceptance.
- B's own profile response contained `Development Recipient`, a null contact email, and `OnlyMe` email visibility.
- Before acceptance B's request for A's shared profile returned `404`. After acceptance it returned the authorized shared profile while contact email, phone, and birthday remained null.
- The test reopened the outbox as B and followed its invitation link through a document load. B remained selected; A did not become active; the invitation preview displayed `Development Adult` and `Development Family`; Accept and Decline were both available; no current A Family context returned.
- Accept returned `200`. The browser's subsequent membership request returned `200` with the invited Family. Profile review appeared without another document load; continuing without changes reached Family, then Home. B remained active throughout.
- After acceptance B's Family members request succeeded and returned B's own membership. No A-private marker or stale A state appeared. Authorization assertions were made against server responses, not inferred from persisted browser identity.
