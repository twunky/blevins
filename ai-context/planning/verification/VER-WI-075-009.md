# VER-WI-075-009 — Trip Audience Removal and Access Enforcement

## Result

**PASS — AC-01 through AC-18 pass.** The fresh-scenario Playwright journey created a Trip as A with B and C selected, verified B's authorized Trip Note, previewed removal of B while retaining C, and confirmed the audience change. Server checks then showed B's Trip list omitted the Trip; B detail, Notes read, and Note creation requests returned the canonical `404`. A retained creator access and could read the existing B-authored Note. C retained audience access. B's refreshed browser Trips view omitted the Trip.

This is automated technical evidence, not human usability evidence. No production Trip behavior, canonical requirement, or human-test status was changed.

## Trip journey evidence

- **Starting state:** A was the active Family administrator. B began with no Family membership in the focused fresh run. C was an active member of the same Family. The default A/B fixture remains unchanged when the Trip opt-in is absent.
- **B setup:** The focused Trip run issued an invitation through the existing API flow, previewed and accepted it as B, then verified A, B, and C were active Family members before Trip creation. The spec also supports the complete serial suite where the earlier invitation test has already made B active.
- **Trip creation:** A created the Trip through the browser. The API response identified A as creator, B and C as selected audience recipients, and A was absent from the recipient list. A, B, and C could retrieve the Trip before removal; B opened the Trip in the browser.
- **Trip Note:** B added a Note through the browser. The API confirmed the Note persisted with B's profile and display name as author. A and B could read it before removal.
- **Audience preview:** A used the audience editor and preview UI. The preview listed B as losing access and C among the resulting recipients. Confirmation succeeded with the server-issued preview token; the saved audience contained C and excluded B.
- **B after removal:** B's authorized Trip list returned successfully without the Trip. Direct Trip detail, Trip Notes read, and a new Trip Note POST each returned HTTP `404`. No post-removal Note was created. After B's UI identity was selected and Trips fetched again, the Trip was absent from the UI list and direct access remained `404`.
- **A and C after removal:** A's list and direct detail requests still returned the Trip. A's Notes read returned the original B-authored Note with content and author unchanged. C's list and direct detail requests still returned the Trip.
- **Stale view:** The test requires server denial for each subsequent protected request and verifies the refreshed B list. It does not require immediate cross-session clearing of already-rendered content or real-time invalidation.
- **Selectors:** Browser interactions use accessible roles, labels, fieldset names, headings, and stable user-facing control names. No CSS layout selectors, positional assumptions, pixel assertions, responsive checks, or screenshot baselines are used.

## Development fixture boundary

Adult C is an explicit Development account/profile with an active membership in A's Family. The startup script's `-IncludeTripAudienceAdult` switch opts the Trip Playwright run into C. The Playwright config omits the switch when only the existing invitation spec is selected and includes it for the Trip spec and complete suite. `CurrentAccountRegistration` exposes/allowlists C only with that opt-in.

The existing SQL-enabled invitation fixture test now also confirms the default scenario still has only A in the Family, B starts outside it, and the identity endpoint exposes only A/B. Development identity tests verify C is accepted only for the opted-in isolated scenario and rejected for a non-dedicated database or non-Development environment. The Trip Playwright run verifies C's actual active membership and audience access. No authentication secret, schema migration, generic fixture system, production identity behavior, or application Trip behavior was added.
