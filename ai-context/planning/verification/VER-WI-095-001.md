## Lock-order correction (2026-10-04)

Real SQL reproduced a deadlock because invitation mutations held an Event read in Serializable while waiting for the Family lock, opposite Event edit's Family-then-Event order. The shared mutation helper now receives a non-authorizing Family target resolved before the transaction, locks Family first inside Serializable, then re-reads canonical Event visibility and verifies the Event still belongs to that Family before membership, role, exact-profile, invitation and Version checks. The coordinated real-SQL regression now passes three iterations each for issue, revoke and RSVP (9/9 overlaps); invitation persistence is 13/13, service/API 24/24, and the full SQL-gated solution is 263/263. ## Scope and implemented model

The new `FamilyEventInvitation` has `Id`, `EventId`, `InviteeProfileId` (Guid), `CreatedAtUtc` (DateTimeOffset), nullable `RevokedAtUtc`, `RsvpStatus` (Pending / Going / Maybe / NotGoing), nullable `RsvpUpdatedAtUtc`, and Guid `Version`. The organizer is the existing Event creator, not a duplicated invitation field. Creation sets Pending and leaves the response time null. Each deliberate response, including Pending, changes Version and sets response time. Revocation changes Version and sets revoked time, preserving the final response. Re-invitation inserts a new ID.

Migration `20261004220426_EventInvitationsAndRsvp` adds only this table, two restricted parent/profile FKs, a four-value status check, unique filtered `(EventId, InviteeProfileId)` where `RevokedAtUtc IS NULL`, an unconditional EventId index for organizer/history queries, and filtered `(InviteeProfileId, RsvpStatus, EventId)` for active discovery. Event and audience schema/data remain separate and unchanged. SQL verifies additive upgrade over a pre-existing Event/audience and repeated migration idempotence. No user database was reset/deleted; disposable SQL-test databases use the existing test convention.

Version is an EF concurrency token. Mutations resolve only the Family lock target before starting Serializable, then acquire Family first and re-read canonical Event access, membership/profile, role, invitation and Version inside the transaction. They verify the Event still belongs to the locked Family. A fresh tracked invitation read avoids stale EF identity-map authority. SQL concurrency conditions prevent an out-of-band stale save. RSVP/revoke races and two-response races permit one current-Version write. A competing membership/audience-loss transaction is observed before the queued RSVP is accepted. There is no generic concurrency framework or retry.

## API and authorization

Successful participation operations return 200 with their actor-specific projection. No authenticated actor gives empty 401; missing/unauthorized Event, role, invitation or target gives empty 404; an eligible actor's duplicate/stale mutation gives empty 409. Invalid approved-state input uses the existing 400 convention. Request Account/organizer/actor fields cannot supply identity. Every endpoint independently checks server access; client hints only affect presentation.

| Endpoint | Current server rule / projection |
|---|---|
| `GET /api/events/{eventId}/invitations` | Canonical Event visibility + active Family membership + exact creator-profile identity. Eligible active adult audience choices exclude self. Named current and revoked invitations include display name and latest RSVP only. No directory/contact/private fields. |
| `POST /api/events/{eventId}/invitations` | Transactional organizer checks above; target is a non-creator, active adult member already in the Event audience. At most one unrevoked record, even during eligibility suspension. Body: InviteeProfileId only. |
| `POST /api/events/{eventId}/invitations/{invitationId}/revoke` | Transactional organizer checks; invitation belongs to the authorized Event, is unrevoked, and Version matches. Repeated revoke cannot rewrite provenance. Target's current eligibility is not required to revoke a retained invitation. |
| `GET /api/events/{eventId}/invitation/mine` | Canonical Event visibility + current active exact profile; returns `{ invitation: own active invitation or null }`. Never returns another profile's record or any named list/count. Revoked rows are retained but this active-action read returns no invitation. |
| `PUT /api/events/{eventId}/invitation/mine/rsvp` | Transactional Event visibility, membership/exact invitee-profile, active invitation, Event/Invitation identity and Version. Body: InvitationId, Version, RsvpStatus. Does not require organizer access. |
| `GET /api/family-groups/{familyGroupId}/event-invitations/mine` | Requested Family's active membership, canonical Event visibility, own exact profile, unrevoked Pending. Minimal InvitationId/EventId/name/date/time. No date expiry. Order: Event date, time, name, ID. |

`EventVisibilityQuery` is shared with existing Event list/item reads and never references invitations. Selected Family, invitation ID, RSVP, editor/admin status and Account resemblance grant no access. Loss of membership or visibility denies invitation access without modifying its history; the same profile restoring both can reuse its still-unrevoked invitation. Organizer loss stops management without freezing independently eligible invitees.

## Frontend ownership and behavior

`src/app/events/event-participation.ts`, `.html`, `.scss`, and `.spec.ts` form the new participation boundary. It receives the already authorized Event plus current profile/Family inputs. It owns organizer invite/list/revoke confirmation, own RSVP controls, protected requests, loading/empty/error/unavailable/success/conflict states and Retry/Refresh. It cancels reads/writes and clears state on input transitions; stale responses cannot populate the new context. Pending writes disable actions. Failed writes require a current protected read; mutations are never silently replayed.

App retains Event creation, cards, existing five-field detail/edit, list, `openRoutedItem`, Family adoption and shell. Only a guarded own-Pending dashboard read/state and authorized-detail component insertion were added. New App state is reset in `clearFamilyScopedState()`. Returning from RSVP detail reloads the dashboard through the existing route lifecycle. No invitation query occurs before routed Event authorization; a failed Event read renders no participation component and does not adopt its Family.
