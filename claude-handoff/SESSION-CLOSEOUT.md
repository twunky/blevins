# Session Closeout

Hand back one concise message suited to the change and the owner's requested format.

- Explain the outcome and material choices; list changed files.
- Report validation actually performed, results, failures, and limitations. Map acceptance criteria to evidence when a work item requires it; do not duplicate the verification record in the message.
- Mention scope conflicts, unresolved risks, or affected deployment dependencies only when relevant.
- Report actual Git status. Owner commits; do not stage, commit, push, or create/update/complete a PR.
- State the item's actual status and any required owner action. Do not declare DONE/PASS or owner approval without the required acceptance; UI items follow their visual-approval requirements.

Small fixes and documentation changes need a short summary and proportional checks. Major features may need a verification record and broader review under their acceptance criteria. Do not automatically require full regression, screenshots, transcripts, a PR description, new governance records, or a follow-up inventory for every session. Preserve existing evidence and reference it rather than recreating it.
